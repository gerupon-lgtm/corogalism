# 迷路の大きさに関する検討用計測

2026-10-06 / T-278 / 対象: ローカルv0.6.19、コード基準 `6fa1b2a025717a7f7dce388c9554532a79b634b4`。

大きな迷路を検証候補から外す必要があるか判断する前に、既存の関数が扱えるサイズと基礎負荷を調べた。[検討資料](../../superpowers/specs/2026-10-06-maze-variation-design.md)の根拠。ゲームの処理・設定は変更していない。新しい面の完成検証や、人間の遊びやすさの判定ではない。

## 生成と経路

[size-generation.json](size-generation.json): 7・8・9・10・11・13・15・17・21の各200標本。これらは測定したサイズであり、許可リストや上限ではない。

- Node.jsで既存 `generateMaze(size, seed)` を実行。
- 乱数の種は各サイズ共通で `seed = i * 137 + 77`、`i = 1..200`。
- 関数内の全セル到達性確認を通過。1,800標本が完了。
- 経路は `maze.pathLength` の通過マス数、曲がり角は `maze.turns`、壁数は既存 `createStage` の壁矩形数。
- 生成時間はPC上の単発処理の標本。端末の時間や描画時間は含まない。
- 表示径は現在のボール直径0.55マスに、盤面幅294または356 CSS pxを掛けてサイズで割った値。実端末の画素数とは異なる。
- やさしい比較は同じ200入力シードで `createStage(generateMaze(7, seed), challengeDifficulty(stage, 'easy'))`。2面と12面を比較した。床テーマ処理による候補の再生成も含むため、最終的な迷路の種が入力と同じとは限らない。
- 中央値などはソートした配列の `floor(標本数 * 割合)` 番目（0開始）。偶数標本の中央2値の平均とは異なる。

## ブラウザの物理と描画

[size-browser.json](size-browser.json): 9サイズ × 2構成 × 2画面密度、36構成。

- WindowsのChrome、Playwright、ローカルHTTP。画面390×844、描画盤面幅356 CSS px。
- ブラウザのCPU処理を6倍遅くする設定。画面密度は1倍と3倍（CSS上の1pxに対応する画素密度）。
- 乱数の種913。`normal` は既存の基本生成、通常床・標準壁、力場なし。
- `iceAssist` は既存 `createStage(generateMaze(size, 913), challengeDifficulty(8, 'easy'))`。現行の候補短縮・配置処理を含む。大盤面向けに調整した新仕様ではなく、配置に残る7×7前提もそのまま。
- 現在のボール・物理値、`dt = 1/60`。更新回数 `i = 0..79` に対し、傾き `x = cos(i/40)*0.7, y = sin(i/40)*0.7`。
- 最初に1回描画。その後80回、物理→描画を同期的に繰り返し、最後60回の処理時間を記録。各構成で同じ方法を使用。
- 動くボールの画像更新を含む。実際の表示間隔や画面合成の時間は測っていないため、`frameMedianMs` は実フレーム間隔やFPSではなく物理＋描画の処理時間。
- ゲームの音声・実センサー・DOM更新・時間とげんき・人間の操縦・長時間負荷は対象外。
- `finite` は座標・速度4値が有限値であること。全36構成でtrue。
- `hits` は既存物理関数の壁ヒット集計値。0でも低速の壁接触がないとは限らない。
- 両画面密度の `pageerror` 記録は空。動作範囲すべての無不具合保証ではない。

11×11は、画面密度3倍で通常床8.4ms、氷＋力場12.7msの中央値。氷＋力場の遅い側5%境界は21.3ms。小さいサイズでも重い例があり、サイズだけを原因と決めない。60回/秒の間隔16.7msを超える条件があるため、実端末の測定と描画改善は今後必要。

最初の描画は約51〜751ms。初期化や初回実行の影響もあるため、サイズ同士の厳密な順位付けには用いない。面開始前の画像準備や描画復元の確認材料とする。
