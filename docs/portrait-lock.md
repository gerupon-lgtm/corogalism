# T-254 縦向き固定（v0.5.7）

本編と検証ページで起動時にScreenOrientation.lock('portrait-primary')をベストエフォートで試す。PWAのmanifestもportrait-primaryを指定。ブラウザ・端末が非対応／拒否しても開始を妨げない。失敗時は端末側の縦向きロックを案内する。

全画面は自動では要求しない。本編の操作の設定、おためしページの操作欄の「縦向きで全画面」をユーザーが押したときだけ全画面化を要求し、その後に縦向き固定を試す。全画面拒否時もロック単独を試す。センサー許可処理とは独立。全画面解除時に再度強制しない。

135テスト成功。既存チュートリアル3幅とセンサー3経路成功。browser-portraitで本編／検証ページそれぞれ自動成功・全画面必須・非対応・拒否の8経路を模擬確認。実端末での固定成功は端末とブラウザに依存し、未確認。

## 本編の面と素材配置について確認したこと

本編はgenerateMazeとstageSeedによりシードから面を生成する。同じシードは再現可能で、チュートリアルと検証面は固定。themes.jsのassignThemeは正解経路の折れ点に接する壁を優先し、外周・開始とゴール付近を除外する。今後、助走距離・進行方向・床や力場の影響範囲・反発先を評価して目的に合う候補へ配置できる。適した候補がない面は配置を減らす／見送る方針が考えられる。T-254では素材配置ルールを変更しない。


## T-255 / v0.5.8 開始操作で全画面化

本編の最初のプラクティス・チャレンジ・チュートリアル開始時に全画面化と縦向き固定を試す。センサー許可要求を先に同じユーザー操作内で開始し、awaitする前に全画面APIを呼ぶ。全画面化の完了をゲーム開始の必須条件にしない。おためしは最初の「傾きで遊ぶ」「画面で遊ぶ」で試す。ページ表示だけでは全画面にしない。

ページ内で自動要求は1回だけ。拒否・非対応・ユーザーによる全画面解除の後に自動で繰り返さない。既存の明示ボタンでは再試行可能。向き固定APIがなくても全画面化だけは試す。起動直後のロック待ちが開始操作を妨げないよう分離。

135テスト成功。browser-start-fullscreenで本編3入口・検証2入口×成功/拒否/非対応の15経路、ユーザー操作中の要求、センサー要求が先行、再要求なしを確認。browser-portraitの既存8経路も成功。実端末での成功はブラウザの許可に依存する。

既存チュートリアルの仮想時計テストは、全画面切替のイベント処理のため開始クリック後に100ms進めてから開始状態を待つよう更新。実際の開始操作では全画面要求の結果を待たない。


## T-256 / v0.5.9 インカメラを避ける余白

本編と床検証ページの全画面表示では、通常の上余白に最低32pxを加える。safe-area-inset-topが32pxより大きい端末ではその値を使い、二重加算しない。通常表示に戻ると32pxの追加を解除する。通常ブラウザ・PWAでも端末のsafe-area通知は尊重する。検証ページにもviewport-fit=coverを指定し、左右と下のsafe-areaも確保。本編の盤面の高さ上限とガイドの高さは上余白を差し引く。実端末でのカメラとの位置関係はユーザー確認待ち。


## T-257 / v0.5.10 上余白の縮小

ユーザーの実機評価で上余白が大きすぎたため、全画面時の上余白を既存余白込みの合計max(32px, safe-area-inset-top)へ変更。本編46px・検証ページ48pxだった最低値を両方32pxへ統一。画像ではステータスバー領域が約60〜70画像pxに見えるが、CSS pxとの倍率は確定できないため実測値とは扱わず、今回32px合計を調整値とする。通常表示と全画面解除時の余白は維持。
