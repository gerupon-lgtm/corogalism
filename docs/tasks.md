## T-101 リポジトリの骨組み

`index.html` / `style.css` / `src/` のディレクトリ構成を作る（`CLAUDE.md` §5）。フェーズ0のプロトタイプを `phase0/index.html` へ移す（**中身は変更しない**。挙動の比較元として残す）。`node --test` が空で通る状態にする。`package.json` を作る場合は `version: "0.1.0"`。

- 完了条件: `index.html` が空の盤面を表示して例外を出さない。`node --test` が成功する
- 検証: ブラウザのコンソールにエラーが出ないこと

## T-102 シード付き乱数と迷路生成（F-121, F-123）

`maze/rng.js`（xorshift32）と `maze/generator.js`（DFSバックトラッカー）。**DOM・描画から独立した純粋関数**。サイズとシードを引数に取る。出力は `docs/data-model.md` の `MazeGraph`。

フェーズ0プロトタイプの `makeMaze()` が動作確認済みの実装なので、これを基に整理する。

- 完了条件: 同じシードで常に同じ迷路が返る。7×7 以外のサイズ（5, 9, 11）でも壊れない
- 検証: `node --test` で ①同一シード＝同一出力 ②セル数が N*N ③外周が必ず壁 ④サイズを変えても例外なし

## T-103 到達可能性検証（F-122）

`maze/validator.js`。BFSで start から全セルへ到達できることを検証する。`generator.js` は検証を通してから `MazeGraph` を返す（**検証を迂回しない**。`CLAUDE.md` §9-2）。

- 完了条件: 検証関数が全セル到達を判定できる。生成経路に組み込まれている
- 検証: `node --test` で ①正常な迷路が合格する ②壁を1枚人為的に足して孤立セルを作った迷路が不合格になる（**不合格を検出できることの確認が要点**）

## T-104 入力の抽象化（F-101, F-104, F-105, F-107）

`input/tiltSource.js`（DeviceOrientation）、`input/pointerSource.js`（擬似傾き）、`input/tiltVector.js`（正規化・平滑化）。両モードの出力を `{x, y}`（大きさ1以下）に揃え、**ゲーム本体がモード差を知らない**形にする。

- 完了条件: モードを切り替えても物理側のコードが変わらない
- 検証: 擬似傾きモードで `localhost` から操作できる。傾きベクトルの大きさが常に1以下（HUDで確認）

## T-105 許可取得・キャリブレーション・フォールバック（F-102, F-103, F-106）

フェーズ0プロトタイプの実装を移植する。**ユーザー操作起点での `requestPermission()`**、拒否・非搭載・無反応時の擬似傾きモードへの着地、プレイ中の再キャリブレーション。

- 完了条件: iPhone XR で許可ダイアログが出て、許可すると傾きで動く。拒否すると擬似傾きモードで遊べる
- 検証: iPhone XR で許可と拒否の両方を試す。PC（センサーなし）で擬似傾きモードに落ちることを確認。**ここで行き止まりを作らないことがフェーズ0で満たした要件**

## T-106 resolveParams とクランプ（F-114）★フェーズ1の中核

`physics/resolveParams.js`。`docs/physics.md` が契約。純粋関数。`config/gameConfig.js` に基準値とクランプ範囲を置く。

**物理コードは `gameConfig` を直接読まず、必ず `resolveParams` の戻り値を使う。** 素材・キャラが1種類のフェーズ1では挙動に差が出ないが、ここを通しておくことが今回の主眼（理由は `docs/physics.md` §1）。

- 完了条件: `docs/physics.md` §8 の4つのテストが通る。物理コード内に `BASE.` への直接参照がない
- 検証: `node --test`。加えて `grep -rn "BASE\." src/physics/` が `resolveParams.js` 以外に出ないこと

## T-107 積分器（F-111, F-113）

`physics/integrator.js`。力を `fx` / `fy` に集約し、加速度→速度→減衰→速度上限→サブステップ分割→位置更新の順で処理する（`docs/physics.md` §6）。`friction` は `v *= Math.exp(-friction * dt)`。

- 完了条件: フェーズ0と同じ基準値で同じ手触りになる
- 検証: `phase0/index.html` と並べて実機で比較する。壁に高速で当てても抜けない

## T-108 衝突解決（F-112, F-136）

`physics/collision.js`。円×矩形の最近点による押し出しと法線方向の速度反射。反発は**壁の素材**から `resolveParams` で解決する。中心が矩形内に入った場合は貫通の浅い軸へ押し出す。壁ヒット数をカウントする（法線方向の速度が閾値を超えたときのみ）。

フェーズ0プロトタイプの `collide()` が動作確認済みなので、これを基に整理する。**セル単位のクランプ方式に変えないこと**（角で抜ける）。

- 完了条件: 通路を高速で移動しても壁を抜けない。角で引っかからない
- 検証: 感度を上限（60）にして全方向へ走らせ、盤外へ出ないことを確認する

## T-109 カメラ抽象とレンダラ（F-124）

`render/camera.js`（`createFixedCamera` のみ）と `render/canvasRenderer.js`。**`cellSize` の計算をカメラに閉じ込め、描画コードが直接計算しない。** 盤面は正方形を保ち、画面比は余白で調整する。devicePixelRatio に対応する。

- 完了条件: 画面を回転・リサイズしても盤面が正方形で崩れない
- 検証: Pixel 6a / iPhone XR / PC で表示を確認。`grep -rn "cellSize" src/render/` がカメラ経由になっていること

## T-110 ステージ・素材・キャラ（F-115）

`world/materials.js`（`default` のみ）、`world/characters.js`（1体のみ、`sizeRatio: 0.55`）、`world/stage.js`（`MazeGraph` から `walls` と `floors` を導出、`zones` は空配列）。`sampleMaterial(stage, actor)` / `sampleZone(stage, actor)` を**1つの関数に閉じ込める**（`docs/physics.md` §7。中心マス方式で実装）。

- 完了条件: 素材やキャラを足す作業が「データを追加するだけ」になっている
- 検証: 試しに `frictionK: 3.0` の素材を1つ定義して全床に適用し、物理コードを1行も変えずに手触りが変わることを確認する（確認後は戻す）
